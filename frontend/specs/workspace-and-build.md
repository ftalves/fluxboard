# Spec: Workspace & Build

This spec defines the repository layout, npm workspace topology, build tooling, and migration plan that the frontend bootstrap depends on. It is the foundation for every other frontend spec: subsequent specs assume the `@fluxboard/domain` package and the Vite-based frontend skeleton described here already exist.

It is also the single source of truth for the **one-time migration** that promotes the existing `backend/src/domain/` directory to a shared workspace package. After the migration completes, this spec describes the steady state.

Wire-level concerns (HTTP, WS) belong to `backend/specs/wire-protocol.md`. Runtime client behavior belongs to the other frontend specs. This document is scoped to *where code lives, how it builds, and how it is tested*.

---

## Goals

1. **One source of truth for domain types and `applyEvent`.** Backend and frontend import the same module so the wire protocol cannot drift between sides.
2. **Independent backend and frontend deployables.** Each builds and tests on its own; neither needs the other installed to run its own scripts.
3. **Zero new package managers.** npm workspaces only — same npm that already exists in the repo.
4. **Minimal churn to the existing backend.** Imports rewrite from a path alias to a package name; otherwise unchanged.

## Workspace root

### `package.json`

```jsonc
{
  "name": "fluxboard",
  "private": true,
  "version": "0.0.0",
  "workspaces": ["packages/*", "backend", "frontend"],
  "engines": { "node": ">=20" },
  "scripts": {
    "build": "npm run build --workspaces --if-present",
    "test":  "npm test  --workspaces --if-present",
    "lint":  "npm run lint  --workspaces --if-present"
  }
}
```

- `private: true` — the monorepo root itself is never published.
- `workspaces` glob covers `packages/*` and the two app dirs. The two apps are listed by name (not globbed) so a future top-level helper directory cannot accidentally become a workspace.
- Root scripts are thin fan-outs over `npm run <x> --workspaces --if-present`. They exist for developer convenience; CI may invoke per-workspace scripts directly.

### `tsconfig.base.json`

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "isolatedModules": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}
```

Each package's `tsconfig.json` extends this and overrides only what is package-specific (`outDir`, `rootDir`, `lib`, `jsx`, `types`, `module` if needed).

The backend currently compiles to CommonJS (`module: "commonjs"`); it keeps that override in `backend/tsconfig.json`. The base config defaults to ESM because that is what the domain and frontend packages want.

### Single lockfile

The repo uses a single root `package-lock.json`. The empty placeholder lockfile at the current repo root (`/home/work/repos/fluxboard/package-lock.json`) is replaced by the real one generated by `npm install` at the root after the migration.

## `@fluxboard/domain` package

### Purpose

Pure functions and types. No I/O. Imported by both `@fluxboard/backend` and `@fluxboard/frontend`.

Public surface:

- All types currently in `backend/src/domain/types.ts` (`Element`, `Arrow`, `DiagramState`, `DiagramEvent` union, individual event types).
- The `applyEvent(state, event): DiagramState` function from `backend/src/domain/applyEvent.ts`.

### `packages/domain/package.json`

```jsonc
{
  "name": "@fluxboard/domain",
  "version": "0.0.0",
  "private": true,
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "test": "vitest run",
    "test:watch": "vitest"
  },
  "devDependencies": {
    "typescript": "^5.4.5",
    "vitest": "^2.0.0"
  }
}
```

- **Source-as-entrypoint.** `main` and `types` point at `src/index.ts`, not a compiled `dist/`. No `"type": "module"` field — the package is module-system-agnostic at the JSON level; consumers compile the TS source themselves.
- **Why source, not compiled output:** the backend runs as CommonJS (`tsc` + `ts-node`) and the frontend runs through Vite. Neither needs precompiled JS from this package. Routing consumers through the TS source eliminates the ESM/CJS interop hazard entirely: each consumer's TypeScript compiler emits whatever module format that consumer needs.
- **Build script.** `npm run build --workspace @fluxboard/domain` still emits ESM `dist/` for future use (publication, type-only consumers), but the dev/test workflow never depends on its output.

### `packages/domain/tsconfig.json`

```jsonc
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "lib": ["ES2020"],
    "types": []
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist", "tests"]
}
```

- `declaration: true` — emits `.d.ts` so consumers get types.
- `types: []` — keeps `@types/node` out of the domain package. Domain code has no Node-specific dependencies.

### `packages/domain/src/index.ts`

```ts
export * from "./types";
export * from "./applyEvent";
```

Barrel only. The two source files keep their current contents verbatim.

### Tests

`backend/tests/domain/applyEvent.test.ts` moves to `packages/domain/tests/applyEvent.test.ts`. The test body is unchanged; the imports rewrite from `@/domain/applyEvent` / `@/domain/types` to relative paths into the package's own `src/`, e.g. `from "../src/applyEvent"`.

Tests run under Vitest, not Jest. Domain tests are pure, and Vitest's Jest-compatible globals (`describe`, `it`, `expect`) cover everything `applyEvent.test.ts` needs.

## Backend changes

### Package name

`backend/package.json` `name` field changes from `"fluxboard"` to `"@fluxboard/backend"`. Version stays. All other fields stay.

### Dependency on domain

Add to `backend/package.json` dependencies:

```jsonc
"dependencies": {
  "@fluxboard/domain": "*",
  "ws": "^8.20.0"
}
```

The `"*"` version range is resolved by npm workspaces to the local package. No publication happens.

### Import rewrites

Every backend import of `@/domain/types` or `@/domain/applyEvent` rewrites to `@fluxboard/domain`. The path alias `@/*` stays in `backend/tsconfig.json` (other directories still use it: `@/realtime/*`, `@/event-bus/*`, etc.), but the `@/domain/*` form disappears.

Files affected (from grep at migration time):

- `backend/src/realtime/protocol/messages.ts`
- `backend/src/realtime/rooms/room.ts`
- `backend/src/realtime/seedValidator.ts`
- `backend/src/event-bus/topics.ts`
- `backend/src/realtime/protocol/parse.ts`
- `backend/src/realtime/rooms/roomRegistry.ts`
- `backend/src/realtime/connection.ts`
- `backend/tests/realtime/rooms/room.test.ts`
- `backend/tests/realtime/rooms/roomRegistry.test.ts`
- `backend/tests/realtime/seedValidator.test.ts`
- `backend/tests/realtime/connection.test.ts`
- `backend/tests/event-bus/bus.test.ts`

The migration script may use `sed` or equivalent. The exact list above is informative — the migrator must regrep at execution time.

### TypeScript module mode

`backend/tsconfig.json` keeps `"module": "commonjs"`. The interop with `@fluxboard/domain` happens through the `paths` alias, not through Node's package resolution.

Add `@fluxboard/domain` to the existing `paths` map:

```jsonc
"paths": {
  "@/*": ["./src/*"],
  "@fluxboard/domain": ["../packages/domain/src/index.ts"]
}
```

The alias points TypeScript directly at the package's source file. Compilation emits `require('@fluxboard/domain')` in the output JS, but no production build runs in MVP (dev is `ts-node`, tests are `ts-jest` — both honor the alias). When a production build is later wired, it will either inline the domain code via a bundler or compile through TypeScript project references; that decision is out of scope here.

### Jest

`backend/jest.config.js` extends its `moduleNameMapper` with one new entry:

```js
moduleNameMapper: {
  "^@/(.*)$": "<rootDir>/src/$1",
  "^@fluxboard/domain$": "<rootDir>/../packages/domain/src/index.ts",
}
```

This is **the primary mechanism**, not a fallback. The mapping resolves the package name to the TS source file, and `ts-jest` compiles it inline as part of the test run. There is no dependency on `packages/domain/dist/`.

### Backend scripts

No change beyond what `npm test` and `npm run build` already do. They run inside `backend/` and produce `dist/` in `backend/dist/`.

## Frontend bootstrap

### `frontend/package.json`

```jsonc
{
  "name": "@fluxboard/frontend",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc -p tsconfig.json && vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "test:watch": "vitest",
    "lint": "eslint 'src/**/*.{ts,tsx}' 'tests/**/*.{ts,tsx}'"
  },
  "dependencies": {
    "@fluxboard/domain": "*",
    "react": "^18.3.0",
    "react-dom": "^18.3.0",
    "react-konva": "^18.2.0",
    "konva": "^9.3.0",
    "zustand": "^4.5.0"
  },
  "devDependencies": {
    "@testing-library/jest-dom": "^6.0.0",
    "@testing-library/react": "^16.0.0",
    "@testing-library/user-event": "^14.0.0",
    "@types/react": "^18.3.0",
    "@types/react-dom": "^18.3.0",
    "@vitejs/plugin-react": "^4.3.0",
    "jsdom": "^25.0.0",
    "typescript": "^5.4.5",
    "vite": "^5.4.0",
    "vitest": "^2.0.0"
  }
}
```

- React 18 (not 19) — `react-konva` has known issues with React 19 reconciler internals; pin to 18 until upstream catches up.
- `konva` is a direct peer of `react-konva`. Pin both.
- `zustand` v4 — v5 has minor API breaks that the store spec doesn't account for.

### `frontend/tsconfig.json`

```jsonc
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "lib": ["ES2020", "DOM", "DOM.Iterable"],
    "jsx": "react-jsx",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "noEmit": true,
    "allowJs": false,
    "types": ["vite/client"]
  },
  "include": ["src/**/*", "tests/**/*"]
}
```

- `noEmit: true` — Vite handles emit. `tsc` runs only as a type-check gate in `npm run build`.

### `frontend/vite.config.ts`

```ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      "/rooms": "http://localhost:8080",
      "/ws":    { target: "ws://localhost:8080", ws: true }
    }
  },
  test: {
    environment: "jsdom",
    setupFiles: ["./tests/setup.ts"],
    globals: true
  }
});
```

- Dev proxy forwards `POST /rooms` and the WS upgrade on `/ws/*` to the backend at `:8080`. The frontend always uses same-origin URLs in dev; CORS does not apply.
- Vitest config merged into `vite.config.ts` via the `test` field (requires `vitest/config` import for full type safety; sample above uses the shared definition for brevity).
- `tests/setup.ts` imports `@testing-library/jest-dom` and any global mocks (e.g. a fake `WebSocket`).

### Environment variables

The backend URL is configurable for production builds:

| Variable | Effect |
|---|---|
| `VITE_BACKEND_URL` | Base URL for HTTP and WS calls in production. Example: `https://api.fluxboard.example`. |

Resolution at runtime (in `frontend/src/net/url.ts`, defined fully in `wire-client.md`):

1. If `import.meta.env.VITE_BACKEND_URL` is set, use it.
2. Otherwise, fall back to `window.location.origin`.
3. WebSocket URL is derived from the HTTP URL by replacing `http://` → `ws://` and `https://` → `wss://`.

In dev, the proxy makes `VITE_BACKEND_URL` unnecessary: same-origin works.

### `frontend/index.html`

Standard Vite template, single `<div id="root">`, single `<script type="module" src="/src/main.tsx">`. Body has zero default styling; the canvas is fullscreen via CSS in `App.module.css`.

## Testing

### Frameworks

| Workspace | Runner | Environment |
|---|---|---|
| `@fluxboard/domain` | Vitest | node |
| `@fluxboard/backend` | Jest (existing) | node |
| `@fluxboard/frontend` | Vitest | jsdom |

The backend keeps Jest to minimize migration churn — its tests, mocks, and config are working today. The two new workspaces use Vitest because it integrates natively with Vite and avoids the ts-jest transform layer.

### Invariants

- Every backend test that passes today must pass after migration. The migrator runs `npm test --workspace @fluxboard/backend` before declaring done.
- The relocated `applyEvent.test.ts` must pass under Vitest in `packages/domain/`. No assertion changes; only import paths.
- `npm test` at the workspace root runs all three suites (domain, backend, frontend).

### Test layout (steady state)

```
packages/domain/tests/applyEvent.test.ts
backend/tests/**/*.test.ts                # unchanged
frontend/tests/**/*.test.ts(x)            # new; structure defined in store.md, wire-client.md, etc.
frontend/tests/setup.ts                   # Vitest global setup
```

The frontend's per-spec test files are introduced as each spec is implemented. This document does not enumerate them.

## Migration plan

The migration is one PR. Steps, in order:

1. **Create root `package.json` and `tsconfig.base.json`.** Move the placeholder `package-lock.json` out of the way (or delete it); `npm install` at the root will regenerate.
2. **Create `packages/domain/`.** Move `backend/src/domain/types.ts` and `backend/src/domain/applyEvent.ts` into `packages/domain/src/`. Add `index.ts` barrel. Add `package.json` and `tsconfig.json` per §"`@fluxboard/domain` package".
3. **Move `backend/tests/domain/applyEvent.test.ts` to `packages/domain/tests/applyEvent.test.ts`.** Rewrite its imports to relative (`../src/...`).
4. **Rename backend package** to `@fluxboard/backend` and add `"@fluxboard/domain": "*"` to its dependencies.
5. **Rewrite backend `@/domain/*` imports** to `@fluxboard/domain` across `src/` and `tests/` (see file list above; regrep at execution time).
6. **Configure interop:** add the `@fluxboard/domain` entry to `backend/tsconfig.json` `paths` and to `backend/jest.config.js` `moduleNameMapper`. Backend `module` setting stays `"commonjs"`. Run `npm test --workspace @fluxboard/backend` to confirm green.
7. **Run `npm install` at the root.** Verify workspace symlinks under `node_modules/@fluxboard/`.
8. **Bootstrap the frontend skeleton.** Create `frontend/package.json`, `frontend/tsconfig.json`, `frontend/vite.config.ts`, `frontend/index.html`, `frontend/src/main.tsx` (renders `<App />`), `frontend/src/App.tsx` (single `<div>` placeholder), `frontend/tests/setup.ts`.
9. **Verify gates:**
   - `npm test --workspace @fluxboard/domain` → green.
   - `npm test --workspace @fluxboard/backend` → green; identical pass count to pre-migration baseline.
   - `npm test --workspace @fluxboard/frontend` → green (with zero tests; placeholder run is acceptable).
   - `npm run dev --workspace @fluxboard/frontend` → boots; opens Vite at `http://localhost:5173`; the placeholder `<App />` renders.
10. **Commit and open a PR.** The PR title is `chore: promote domain to @fluxboard/domain workspace`. The PR body links to this spec.

The migration must produce **no behavior change** in the backend. If a test that passed before fails after, the migrator stops and fixes before continuing.

## Invariants (steady state)

- **One lockfile.** `package-lock.json` lives only at the repo root. Per-workspace lockfiles must not exist.
- **No circular workspace deps.** Backend and frontend both depend on domain. Domain depends on neither.
- **`@fluxboard/domain` has no runtime dependencies** outside the standard library. Only `devDependencies` (TypeScript, Vitest).
- **Backend and frontend never import each other.** The only shared code path is `@fluxboard/domain`. Cross-import is a build-time error to be caught in review.
- **Path alias `@/` is backend-internal.** Frontend does not use it; if a frontend file needs a deep import, it uses a relative path. Domain imports cross the package boundary via `@fluxboard/domain` only.

## Out of scope (MVP)

- Publishing `@fluxboard/domain` to a registry. The package stays private.
- A compiled `dist/` consumed by Node directly. The package exposes its TS source through `main`; the `build` script exists for future use.
- Backend production build wired to use the domain package. Dev (`ts-node`) and tests (`ts-jest`) both work today; a production `tsc` → `node dist/` pipeline is out of scope for this spec.
- Turborepo / Nx / Lerna. Plain npm workspaces are sufficient at this scale.
- A `packages/shared` for non-domain utilities (logging, ids, time). If a use case emerges, a new spec will define it.
- TypeScript project references. Each workspace compiles independently; cross-package references go through the published `dist/` of `@fluxboard/domain`.
- Vitest UI mode, coverage reports, or snapshot testing for the frontend.
- Storybook or component playground.
- Production deployment topology (Docker, hosting, CDN). The build outputs are static assets; how they are served is out of scope for this spec.
